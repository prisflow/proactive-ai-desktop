# 架构评估：Claude Code · Hermes Agent · 本方案

## 概述

本方案定位为 Claude Code 的 Agent SDK 与 Hermes Agent 之间的中间形态。三者都采用"单智能体循环 + 工具调用"的核心范式，但在编排方式、上下文管理、工具约束三个维度上有显著差异。

---

## 一、Claude Code Agent SDK

核心是一个**工具调用循环**（Tool-calling Loop）：

```
用户输入 → 系统提示 + 工具定义 + 对话历史 → LLM 评估
  → 调用工具 → 工具结果回填 → LLM 再次评估
  → 重复直到 LLM 输出无工具调用 → 返回最终结果
```

关键特征：`max_turns` / `max_budget_usd` 控制循环、自动上下文压缩、子智能体独立上下文、MCP 扩展工具、只读工具可并行、生命周期钩子（PreToolUse / PostToolUse 等）。

**设计哲学**：LLM 全权决策，松约束，线性 turn，外部化扩展。

---

## 二、Hermes Agent

Python 实现，核心也是工具调用循环，但多了**技能系统**和**记忆循环**：

```
用户输入 → LLM 决策 → 调用工具
  ├─ 普通工具 → 结果回填 → LLM 继续
  ├─ 技能系统 → 自动创建/改进技能
  └─ 记忆系统 → 周期性整理 + 用户画像
```

关键特征：40+ 内置工具、技能从复杂任务自动创建并在使用中自我改进、FTS5 会话搜索、单个网关服务多平台（Telegram/Discord/Slack/CLI）、内置 Cron 调度、子智能体并行。

**设计哲学**：自改进循环、平台无关、低成本持续运行。

---

## 三、三维度对比

### 编排方式

| 维度 | Claude Code | Hermes | 本方案 |
|---|---|---|---|
| 流程控制 | LLM 自主决策 | LLM 自主 + 技能/记忆回路 | 事件类型决定 Handler 路径 |
| 非线性能力 | 无（严格线性 turn） | 日程/记忆侧链路 | 事件本身就是非线性路由 |
| LLM 必经率 | 100%（每步都要 LLM） | 100% | 非必经（Static Handler 绕过） |

**本方案差异点**：Static Handler 可以绕过 LLM 直接执行，对高频低决策开销场景（日志、通知、状态更新）更高效。

### 上下文管理

| 维度 | Claude Code | Hermes | 本方案 |
|---|---|---|---|
| 层级数 | 2（主/子） | 3+（主/技能/记忆） | 2（主/子） |
| 切换方式 | 子智能体（独立 LLM 上下文） | Python 子进程 | 事件驱动（总线路由） |
| 切换代价 | 高（独立上下文满载） | 中 | 低（总线内存路由） |
| Agent 是否感知 | 不感知子智能体内部 | 不感知 | 自己负责切换和退出 |

**本方案差异点**：Agent 知晓自己在哪个上下文中运行并负责退出——Claude Code 和 Hermes 的子任务是"委派出去就不管了"。

### 工具系统

| 维度 | Claude Code / Hermes | 本方案 |
|---|---|---|
| 工具含后续逻辑 | 允许 | 不允许 |
| 工具具决策能力 | 有 | 无 |
| 工具生产事件 | 无（结果回填 LLM） | 有（结束时生产事件到总线） |
| 可见性控制 | 全部全局 / 工具集切换 | 全局 + 上下文私有两级 |

**本方案差异点**：工具不含后续逻辑、不具备决策能力，是最核心的设计约束。决策权统一收归 Handler，工具是纯粹的"执行 + 报告"单元。

## 四、方案定位

| 维度 | Claude Code 端 | 本方案 | Hermes 端 |
|---|---|---|---|
| 编排复杂度 | 低（线性） | **中**（事件驱动） | 高（多层回路） |
| 工具约束 | 松 | **紧** | 松 |
| 插件生态 | MCP（外部化） | **子上下文（内置化）** | 技能系统（内置化） |
| 可预测性 | 中 | **高** | 低 |
| LLM 依赖度 | 高 | **中**（有绕过路径） | 高 |

### 独有优势

1. **事件总线的可观测性**：每条事件可记录到 LogService，天然形成执行轨迹
2. **Static Handler 效率**：避免不必要的 LLM 调用，节省 token 和时间
3. **两层扁平上下文**：避免深度嵌套，插件注册即用
4. **工具约束的安全性**：工具不决策，不会有递归失控风险

### 潜在风险

1. **事件总线单消费者 + FIFO 高吞吐瓶颈**：需实现 drain 链上限保护
2. **上下文切换事件化增加心智负担**：Agent 需理解事件驱动的上下文生命周期
3. **工具约束可能过度**：简单条件逻辑也要提到 Handler 层，增加了 Handler 注册的复杂度
4. **插件开发门槛高于 MCP**：插件需理解事件系统、上下文注入、Handler 注册

---

## 五、适用场景

| 系统 | 最佳场景 |
|---|---|
| Claude Code | 编程助手、文件操作密集型任务 |
| Hermes Agent | 长期运行、自进化、多平台接入的个人助手 |
| 本方案 | 结构化对话、UI 分发、插件扩展的桌面应用 |
