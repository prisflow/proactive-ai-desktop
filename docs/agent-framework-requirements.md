# 智能体框架需求文档

## 核心定位

一套事件驱动的智能体（Agent）框架，以对话工具对外暴露，同时提供若干内置内容模块。框架的两个核心设计：

1. **上下文切换管理**（Context Switching）
2. **事件总线替代静态链路/图**（Event Bus over Static Graph）

---

## 一、上下文系统

### 1.1 架构

- **两层扁平结构**：主上下文（Main Context）↔ 子上下文（Sub Context）
- 子上下文不可再嵌套
- **有且只有一个智能体在运行**，它自己负责切换和退出子上下文

### 1.2 切换逻辑

上下文切换类比 OS 的 CPU 上下文切换：
- 进入子上下文时保存主上下文的执行状态
- 退出子上下文时恢复主上下文
- 上下文切换不会并行执行

### 1.3 子上下文分类

| 类型 | 说明 |
|---|---|
| **内置型** | 由宿主/框架开发者编写 |
| **插件型** | 通过注册接口注入 |

### 1.4 生命周期

子上下文的**创建、销毁、切换全部由事件驱动**。

### 1.5 上下文实例属性

每个上下文（无论主/子）独立拥有：

- **事件系统**：该上下文可识别和处理的事件类型集合
- **初始提示词**（Initial Prompt）：进入该上下文时注入的系统提示
- **工具集**（Tool Set）：该上下文可见的工具列表
- **Handler 注册表**：事件到 Handler 的映射
- **私有存储空间**：上下文私有的状态/数据

### 1.6 插件与上下文

- 插件统一使用子上下文暴露
- 不区分"对话级"和"全局级"
- 插件注册时需将自定义事件注入主上下文，主上下文据此路由

---

## 二、事件总线

### 2.1 定位

事件总线取代传统的静态链路或 DAG 图编排。智能体的执行流程完全由事件驱动，而非预定义的有向图。

### 2.2 特性

- **单消费者**（唯一的 Agent 实例）
- 严格 **FIFO**，无事件优先级，无插队
- 事件类型为开放字符串，不封闭
- 工具生产的事件有固定格式约束（具体格式在实现阶段定义）
- 工具在**执行结束时生产事件**（不推进度，不做轮询）
- 插件可将自定义事件注入主上下文的事件系统

---

## 三、Handler

### 3.1 职责

Handler 是**转换器/分发器**（Translator/Dispatch），根据事件类型决定后续路径。Handler 本身不执行实际业务操作，实际执行由 Tool 完成。

### 3.2 两种类型

| 类型 | 行为 | 适用场景 |
|---|---|---|
| **LLM Handler** | 将事件转换为 LLM 输入，通过标准的函数调用机制告知 LLM 当前上下文可选用的后续工具 | 用户输入、子任务完成等需要 LLM 决策的场景 |
| **Static Handler** | 执行纯逻辑操作，不涉及 LLM 调用 | 日志记录、状态更新、UI 通知、数据持久化等副作用操作 |

### 3.3 Static Handler 的设计理由

Static Handler 的存在是本方案区别于 Claude Code 和 Hermes 的关键设计之一。在 Claude Code 和 Hermes 中，所有操作都必须经过 LLM 决策 turn。本方案通过 Static Handler 提供了一条**绕过 LLM 的路径**：

- **效率**：不需要 LLM 参与的副作用操作（如记录日志、更新 UI 状态、发送通知）直接执行，节省 token 和时间
- **原子性**：Tool 保持纯执行单元，不包含后续逻辑，不具备决策能力。Static Handler 承载"执行完 Tool 后需要做什么"的逻辑
- **可观测性**：Static Handler 的执行路径同样经由事件总线，与 LLM Handler 共享同一条可观测链路

### 3.4 处理路径

- **LLM Handler** → LLM 决策 → 调用 Tool → Tool 结束事件 → 回到 Handler
- **Static Handler** → 直接执行逻辑（不需要经过 LLM）

---

## 四、工具系统（Tool）

### 4.1 核心约束

- 工具**不包含内联后续逻辑**
- 工具**不具备决策能力**
- 例如：流式回复工具只能输入提示词 → 输出流式结果，不能根据结果自动决定下一步
- 条件分支等逻辑必须上提到 Handler 层

### 4.2 设计理由

将工具约束为"无状态、原子化的执行单元"，决策权统一收归 Handler（LLM Handler 走 LLM，Static Handler 走代码逻辑）。这是本方案可预测性的核心来源。

### 4.3 执行结束

- 工具执行结束时向当前上下文的事件总线生产一个事件
- 该事件触发 Handler，驱动后续流程

### 4.4 执行模式

| 模式 | 说明 | 是否生产事件 |
|---|---|---|
| **异步** | 长时间运行，结束时生产事件 | 是 |
| **同步** | 瞬时完成（如 Toast），可按需生产事件 | 可选 |

### 4.5 可见性

- **全局工具**：所有上下文可见
- **上下文私有工具**：仅在当前上下文范围内可见

---

## 五、流程循环

### 5.1 标准流程

```
事件 → Handler(类型判断)
         ├─ LLM Handler → LLM 决策 → 调用 Tool
         │                                ↓
         │                         Tool 结束事件 → 回到顶部
         └─ Static Handler → 直接执行（不经过 LLM）
```

### 5.2 终止机制

- LLM 调用一个内置的**结束工具**来声明"本轮处理完毕，等待下一个事件"
- 该结束工具是防止事件倒灌死循环的终止点
- 调用后等同此轮处理结束，等待新的事件进入总线

---

## 六、非流式响应与内置 UI 系统

### 6.1 插件接入接口

- 插件侧的 LLM 接入使用**非流式响应接口**
- 框架负责将非流式结果处理为适当的形式呈现

### 6.2 非流式响应处理

- 非流式 LLM 响应**不流式推送**
- 作为最终结果直接呈现

### 6.3 内置 UI 系统

- 配套一套**内置简易 UI 系统**，提供多个 UI 组件
- 非流式结果经过处理后放入 UI 组件，通过框架的分发机制发送到前端渲染
- 这套 UI 系统用于插件的 UI 分发场景

---

## 七、插件规范

- 插件统一使用子上下文暴露
- 不区分"对话级插件"和"全局级插件"
- 插件声明自己的事件类型、工具集合、初始提示词
- 插件注册时需将自定义事件注入到主上下文的事件系统
