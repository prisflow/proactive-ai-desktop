# 主动对话与统筹：总体架构

## 1. 主智能体

主智能体是整条智能体链路的调度核心，职责可以概括为三件事：**读记忆、收信号、做决定**。

读记忆，是指同时参照「对话里已经说过什么」和「当前局面里记着什么」（见下一节两个记忆模块），形成对上下文的判断。收信号，是指所有「该轮到系统反应一下」的入口，都先变成统一格式的信号递进来，而不是散落在界面或各处逻辑里各写一套。做决定，是指是否调用模型、是否委派给子智能体、是否只更新记忆而不对用户说话、以及多路结果如何合并成最终对用户可见的一条或几条消息。

没有主智能体这一层，就只能靠单一模型一路生成到底：扩展子能力时没有统筹方，并发任务时也容易互相堵死。主智能体不要求自己完成所有推理，但必须**拍板**——谁可以并行干活、谁先谁后、最后以谁的名义、用什么语气写进对话。

子智能体（以及将来的更多角色）由主智能体按需调用；它们向主智能体交回可合并的结果，而不是各自直接抢占用户对话流。子智能体的细节本稿不展开，但主智能体与它们的关系是：**一个主控、多个可并行的执行单元**，主控负责合并与节奏。

## 2. 两个记忆模块

记忆拆成两块，**平级、分工不同**，都由主智能体在决策时读写，但用途不要混用。

**对话记忆**：面向用户可见的往来内容——说了什么、谁先谁后、用于拼上下文和续写。它的核心是「聊天记录」这一时间线，解决的是模型和用户之间**字面上下文**是否连贯。

**局面记忆**：面向系统内部状态——聊到第几阶段、主动开口的冷热与冷却、当前话题权重、剧情或关系类标记、以及任何不适合原样写进聊天记录、却影响「该不该说、该谁说」的信息。它的核心是**结构化局面**，解决的是**策略与节奏**，避免把系统状态硬塞进提示词或和对话原文搅在一起。

两块记忆都要能持久化、能随会话恢复；主智能体在一次决策里可能只改其中一块，也可能两块都改。以后若要加「总结压缩」，也应分别约定：对话记忆做摘要时保留对用户叙事的连贯，局面记忆做摘要时保留对决策仍关键的字段，而不是混成一个大杂烩表。

## 3. 事件总线与钩子

**事件总线**是外界与内部各类「发生的事」进入主智能体之前的统一入口。用户长时间无操作、计时器到期、将来插件或界面反馈——都应先变成**带类型、带载荷、带来源**的事件，进入总线，再由主智能体或中间策略消费。

这样主动对话才不会退化成「只有一个时间间隔变量」：间隔只是事件的一种；多种事件可以排队、合并或按优先级处理，主智能体看到的是**事件流**，而不是散落的回调。

**钩子**挂在总线之后、主智能体决策与写记忆的全流程上：事件入队前后、是否响应的判断、调用子智能体前后、写入对话记忆或局面记忆前后、以及出错时如何处理。钩子的用途是让扩展在**不改写主流程骨架**的前提下插入校验、改写载荷、打日志或做降级；第一版可以只实现少量空位，但架构上要预留，否则以后每加一类能力都要改核心分支。

事件总线 + 钩子的组合，把「输入」和「流程上的扩展点」定死；主智能体专注于策略与合并，而不是被各处硬编码拖散。

## 4. 插件注册

插件不直接绕过主智能体改对话或改记忆。插件通过**注册**进入体系：声明自己关心哪些事件、在哪些钩子上提供逻辑、以及是否有子智能体或额外能力供主智能体调用。

注册完成后，插件成为总线上的**事件生产者**或**钩子消费者**（或两者兼有）。主智能体仍保留否决权与合并权：插件可以提议、可以上报信号，但**对用户可见的发言与对两块记忆的正式写入**，应经主智能体所在链路统一处理，避免多头发话、状态打架。

本阶段不要求把插件种类一次设计完；架构上只要求：**注册是插件进入系统的唯一规范入口**，与主智能体、双记忆、事件总线、钩子对齐，后续再逐项补具体插件类型。

## 5. 小结

| 构件 | 作用 |
|------|------|
| 主智能体 | 读双记忆、消费事件、调度子智能体、合并结果、拍板对用户输出与记忆更新 |
| 对话记忆 | 用户可见往来的时间线，服务字面上下文 |
| 局面记忆 | 内部结构化状态，服务策略与主动节奏 |
| 事件总线 | 统一输入，支持多源事件而非单一时间间隔 |
| 钩子 | 流程上的扩展点，便于演进而不碎裂主链路 |
| 插件注册 | 规范插件如何接事件与钩子，不绕开主智能体 |
